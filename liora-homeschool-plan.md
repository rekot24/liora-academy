### Multi-Semester Framework

The portal handles successive semesters across school years. Each semester is self-contained. Past semesters are archived as read-only (for CHEC portfolio).

```
School Year 2025–2026
├── Semester 0: Summer Catch-Up     May–Jul 2026  [LITE mode]
├── Semester 1: Fall 2026           Aug–Dec 2026  [FULL mode]
└── Semester 2: Spring 2027         Jan–May 2027  [FULL mode]

School Year 2026–2027
├── Semester 1: Fall 2027
└── Semester 2: Spring 2028
```

**Semester modes:**
- **LITE** — Math + reading only, no compliance warnings, casual life skills logging, days still counted
- **FULL** — All 8 subjects, compliance tracking active, full scheduler, pace alerts

**Global vs. semester-scoped data:**
- Skills checklist and job site log are **global** — span all semesters, never reset
- Schedule, assignments log, and pace tracking are **semester-scoped**
- Master curriculum library is **global** — loaded once, used across all semesters

**Admin semester controls:**
- Create new semester (name, dates, mode)
- Switch active semester
- Archive completed semester (read-only)
- View any past semester for portfolio/CHEC

## What prompted this

Summer ended with a working but summer-lite version of the portal live. Before Fall, Joshua wanted a full walkthrough of what existed vs. what was needed, given real decisions had landed since the April spec:

- **CHEC enrollment is done** — filing layer resolved, attendance record-keeping now has to actually hold up
- Both Joshua and Liora are neurodivergent (Joshua: business owner + ADHD-adjacent flexibility needs; Liora: ADHD) — the schedule needed to be genuinely non-standard, not just "flexible in theory"
- Job Site Log wasn't pulling its weight as the primary "extra school day" concept anymore — replaced by Field Trips (educational outings) as the more accurate compliance-relevant concept, with Extracurricular Activities (sports, Jiu Jitsu, etc.) split out as a separate, non-attendance-counting thing

## Key decisions made

| Decision | Outcome |
|---|---|
| Schedule structure | Fully admin-editable: recurring weekly pattern (any day, weekends included) + per-day manual overrides that survive regeneration |
| Attendance compliance | A day counts if 1+ scheduled item is completed OR a flagged field trip happens that day — looser than "all items done," which is tracked separately |
| Job Site Log | **Removed.** Replaced by Field Trips (counts toward attendance, optional) and Extracurricular Activities (does not count, for things like Jiu Jitsu) |
| Curriculum editing | Courses & Life Skills are now fully admin-editable in the UI (not hardcoded in source) — add/edit/delete, grouped by category/subject, with search and sort |
| Bulk curriculum loading | Real CSV bulk-import built into Courses & Subjects, since manual one-by-one entry doesn't scale for platforms like Khan Academy with 100+ lessons. Claude can also draft a starter CSV on request — tell it the platform/subject/grade level |
| Required subjects | All 9 Colorado-required subjects (Reading, Writing, Speaking, Math, Science, History, Civics, Literature, US Constitution) are pre-loaded and locked from deletion, only editable. Speaking is activity-based (job site conversations, presentations, field trip discussion) rather than lesson-driven |
| Evaluation reminder | 7th grade evaluation (required this year, due ~April 2027) is a persistent banner across every screen — but date-gated to only appear starting ~March, so it's not visually pinned for 7 months. Stays until marked scheduled/complete |
| Alerts | Per-assignment reminder times → browser Notification popup (tab must be open) + Apollosign display flag. Phone push was considered but deferred — would need n8n (not yet set up) as the trigger-to-notification bridge |
| Data safety | Everything is still browser localStorage (see below) — added a real auto-save-to-file layer (File System Access API, Chrome/Edge) so it mirrors to one real file on disk automatically, instead of relying on memory alone or piling up dated manual exports |
| Chores/tasks for the whole family | **Deliberately kept separate.** This app's data model assumes one student + one admin; multi-user would mean rebuilding the foundation, not adding a feature. ## Current architecture

- **Stack:** React (Vite), single-file `App.jsx`, deployed as a static build — no backend, no server-side code
- **Data storage:** ⚠️ **Superseded again, August 2026** — see "Shared Server Sync" note directly below. Was pure browser `localStorage`; now a shared JSON file on the server is the real source of truth, with localStorage as a fast local cache.
- **Backup:** Two layers —
  1. **Auto-save to file** (recommended): connects to a real file on disk via the File System Access API (Chrome/Edge only), silently rewrites it on every change. Put that file in a Google Drive/OneDrive-synced folder for automatic offsite backup with zero extra infrastructure
  2. **Manual export/import** (.json): works in any browser, fallback for Firefox/Safari or moving data between devices
- **Hosting:** Same as before — static build uploaded to the Hostinger subdomain (`school.theflairhub.com`)

### Shared Server Sync (added August 2026, right after the Fall rebuild)

The original Fall 2026 rebuild still had each device (PC, phone, Apollosign) keeping its own private `localStorage` — meaning nothing synced between devices at all. That became a real problem once the plan was "edit on the PC, but also check things off directly on the Apollosign and have it stick everywhere."

**What changed:** added a tiny PHP endpoint (`server/api.php`) that reads/writes one JSON file (`server/data/state.json`) on the Hostinger server. Every device now:
- Fetches that shared file on load and hydrates its live state from it (not just localStorage)
- Polls it every ~25 seconds to pick up changes made elsewhere
- Pushes its own changes to it (debounced ~1.2s after the last edit), same trigger point as the existing `save()` helper

localStorage didn't go away — it's still written on every change as an instant-paint cache for that device, and it's still what the File System Access auto-save and manual export/import read from. But it's no longer the *authoritative* copy; the server is.

**Auth:** a shared key (`API_KEY`) baked into both `App.jsx` and `api.php` — client-side secrets can't be truly hidden in a static site, so this is obscurity-grade protection (blocks casual scanning, not a targeted attacker), which is an appropriate tradeoff for a private family tool with no PII beyond ordinary school records.

**New tradeoff:** the app is no longer fully offline-capable. It needs network access to Hostinger to load/save current data. Given it's used at home with normal internet, this was judged an acceptable tradeoff for getting real cross-device sync (including phone access for Joshua and Liora) without standing up heavier infrastructure like n8n or a real database.

**Deployment note:** deploying now means uploading *two* things — the usual `dist/` build to the site root, and the `server/` folder (containing `api.php` and a `.htaccess`-protected `data/` folder) alongside it. The server folder only needs to go up once; after that, only `dist/` needs to be replaced on future updates.

### localStorage keys (for future reference / debugging)
```
hs_semesters           — semester definitions (name, dates, mode, target days)
hs_active_semester     — which semester ID is currently active
hs_assignments         — courses catalog (the editable curriculum, by subject)
hs_skills_catalog      — life skills catalog (editable, by category)
hs_schedule            — the generated day-by-day schedule (date → assignments)
hs_overrides           — per-day manual overrides (date → items, or "SKIP")
hs_pattern             — recurring weekly pattern (subject → days of week)
hs_log                 — completion log (date → assignmentId → done/skipped)

```

## Bugs found & fixed (August 2026, post-deploy)

- **"Clear day" permanently blacklisted the day instead of just emptying it** — the only button in the Day Override Editor for emptying out a day was labeled "Clear day," but it called `onSetOverride(dateKey, "SKIP")` — the same mechanism used to mark a genuine day off (a holiday). "SKIP" is still an override, so once set, that day is permanently excluded from ever being auto-filled by the recurring pattern again — there was no way back from the UI. This is exactly what happened to the sample seed data on the four Mondays: clicking "Clear day" on each one emptied them, but also quietly locked them out of pattern generation forever, which is why Constitution's regenerate skipped straight past all of them. Fixed by splitting the one ambiguous button into two clearly labeled, separately confirmed actions in the Day Override Editor: **"🚫 Skip day (day off)"** — same as before, for actual holidays/days off, permanent until reset — and **"↺ Reset to pattern"** (new) — fully removes the override (via a new `"RESET"` case in `handleSetOverride`) so the day goes back to being a normal, auto-filled day the next time you regenerate. The Reset button only shows up when the day currently has an override. **Action needed:** the four Mondays affected by the original seed cleanup still have the old permanent SKIP override sitting on them — open each one in the Day Override Editor and click "Reset to pattern" to release them back to the pattern, then regenerate.
- **Regenerate silently jumped past dates because of manual overrides — no bug, but no explanation either** — by design, "Manual override wins outright": if a date already has a hand-edited day (via the Day Override Editor), regenerating never touches it, for *any* subject, even if the override has nothing to do with the subject being generated. So when Joshua regenerated just Constitution starting today and it landed on 9/14 instead, the real cause was that the Mondays in between already had manual overrides from earlier testing — each one silently absorbed that week's Constitution slot and pushed the item to the next open Monday. That's intentional (hand edits should survive regeneration) but was invisible in the result popup. Fixed by having `generateSchedule` count `overriddenSkips` — days in the regenerated range that would've received a slot for the subject(s) being generated but were skipped because of an existing override — and surfacing that count in the "Save pattern & regenerate" result popup with a pointer to check the calendar's "Manually overridden" days. No behavior changed, just visibility.
- **No way to clear scheduled-but-incomplete items** — added a "🗑 Clear scheduled (incomplete)" button next to Save pattern & regenerate in Schedule Builder, reusing the same Date/Subject fields. It removes not-yet-completed items for the chosen subject (or every subject) from the chosen date forward — including pulling matching items out of manually overridden days, so a future regenerate can fill those slots again instead of the override silently restoring what was just cleared. Completed/graded items are never touched, and it requires a confirmation dialog (stating the scope and that it can't be undone) before anything is removed.

- **"Skills Learned" count didn't go down when a skill was unchecked** — the `skills` state object stores two kinds of entries side by side under flat keys: `skillId: true/false` (the checkbox) and `skillId_date: "2026-08-15"` (when it was checked). `handleToggleSkill` wrote the `_date` entry when checking a skill but never removed it when unchecking — so an unchecked skill left a stale, truthy date string behind. The Overview/dashboard "Skills Learned" stat then computed its count as `Object.values(skills).filter(Boolean).length`, which blindly counts *every* truthy value in that object — so those leftover date strings kept getting counted as if the skill were still done, even after the checkbox was cleared. Fixed both sides: `handleToggleSkill` now deletes the `_date` entry on uncheck, and the count itself now derives from the actual skill catalog IDs (`allSkillIds.filter(id => skills[id]).length`) instead of blindly counting the whole object — so it's correct going forward even if other stray keys ever end up in that object again. No data migration needed; any already-stale `_date` entries from before this fix are simply ignored by the corrected count.

- **"Days Completed" / "Days Done" stats weren't measuring attendance — they measured perfect days** — the Overview tab, the student's daily dashboard, and the Apollosign's "Semester Progress" bar all counted a day only if *every* scheduled item that day was checked off (`scheduled.every(...)`). But all three of those stats are shown against `targetDays`, which is the semester's 172-day-style attendance target — and per the Fall 2026 rebuild decision, attendance only requires **1+ item completed or a counted field trip**, which is exactly what `isAttendedDay()` already implemented correctly (it just wasn't being used consistently). Joshua noticed this when a completed reading assignment didn't move the Overview number. Fixed by switching all three "days" counters to `isAttendedDay()`, and relabeled the Overview/dashboard stats to "Days Attended" so they can't be mistaken for attendance again. The `deleteLesson`/streak logic elsewhere intentionally still uses "all items done" for its own "day streak" stat — that's a separate, correct concept (a perfect-completion streak), left as-is.
- **Attendance tracking existed as raw data but had no browsable view** — `schedule[date]` + `allLog[date]` already captured exactly what was scheduled and completed each day, but the Attendance tab only showed a checkmark on a calendar with no way to see *what* happened on a given day. Added: (1) clicking any day with data (calendar or new list view) opens a detail panel listing every scheduled item, its done/not-done state, and any recorded grade, plus field trip info if one happened that day; (2) a new List view alongside the existing Calendar, showing every relevant day chronologically with an "Attended / Not attended" badge and an "X/Y items completed" summary, for scanning history without paging through months.

- **Bulk CSV import had no duplicate check** — `importRows` in `CourseManager` appended every row from the uploaded CSV unconditionally, so re-uploading the same file (or a file overlapping the existing catalog) doubled up lessons with no warning. Fixed two ways:
  1. **Going forward:** `importRows` now builds a seen-set per subject keyed on `title|platform` (case-insensitive, trimmed) — seeded from the existing catalog and updated as rows are added — and skips any row that matches. The import result now reports both counts, e.g. "Imported 40 lessons. Skipped 40 duplicates (already in the catalog or repeated in the file)." The Bulk Import modal's subtitle was updated to say it's now safe to re-upload the same file.
  2. **Cleaning up existing duplicates:** added a "🧹 Remove duplicate lessons" button next to Bulk Import in Courses & Subjects. It scans every subject for `title|platform` duplicates, keeps the first occurrence, re-sequences what's left, and also removes the duplicate IDs from any day they'd already been scheduled on (via the existing `onRemoveFromSchedule` plumbing) — with a confirm dialog showing the count before it touches anything.

- **(Restored) Grading system** — `LessonEditModal` has a Grading dropdown (None / Pass-Fail / Score, with a "Score out of" field when Score is chosen). Checking off a graded assignment — on the PC dashboard or the Apollosign — now opens `GradeEntryModal` to capture a result before marking complete, with a "Skip grading" escape hatch. Recorded grades show as a badge on `AssignmentCard` and on the Apollosign assignment tiles. Data lives in a new `grades` state (`hs_grades` in `STORAGE_KEYS`), flows through the same `hydrateFromSnapshot`/server-sync/backup plumbing as everything else automatically. While restoring this, also re-confirmed and restored a related fix from the same lost session: **the Apollosign alert-flag banner was wired in but never actually rendering** — `alerts`/`alertSettings` were being passed into `ApolloSignDisplay` as props but nothing read them. Fixed by computing `activeFlags` (today's assignments whose alert time has passed and aren't done) and rendering a reminder banner above the progress section.

- **Uploaded App.jsx was missing an entire chunk of prior work** — the file Joshua handed back for a fix session turned out to predate the whole scheduling-system upgrade (date/subject-scoped regeneration, "reschedule missed items" mode, the safety cap + result popup) and the dropdown-readability `index.css` fix. Likely cause: an out-of-date local copy got re-uploaded instead of the last delivered version. Reconstructed all of it from prior chat history and rebuilt from source. The grading system was also confirmed missing and has now been restored too — see the four restored items below.
- **(Restored) Deleting a lesson didn't remove it from an already-generated calendar** — see the entry below from the same session; folded in here since it landed in the same restoration pass.
- **(Restored) Schedule regeneration** — `generateSchedule` now takes `startDate`, `subjectFilter`, and `rescheduleMissed`, returns `{ schedule, stats }`, and carries a hard 3,000-iteration safety cap so a malformed semester date range can never hang the browser. The Schedule Builder UI has a date picker, a subject dropdown ("all subjects" vs. one), and a "Reschedule missed items too" toggle, plus a `regenerating` button state that yields to the browser before running so it can paint a loading label first. Clicking regenerate now shows a real summary popup (items rescheduled, days filled, days preserved, safety-cap warning if hit) instead of giving no feedback at all.
- **(Restored) Dropdown readability** — `index.css` had dead scaffold CSS with `color-scheme: light dark`, which made native `<select>` popups render light-on-white regardless of the app's own dark theme. Replaced with a minimal stylesheet that forces `color-scheme: dark` and explicitly colors `<select>`/`<option>`, and wired it into `main.jsx` (it wasn't being imported at all in the uploaded copy).
- **Deleting a lesson didn't remove it from an already-generated calendar** — `deleteLesson` in `CourseManager` only filtered the lesson out of `coursesCatalog`; the schedule stores its own independent copy of each assignment per day (spread off the lesson at generation time), so nothing touched those copies. - **CSV bulk import silently dropped Level and Minutes** — `importRows` checked `r.level`/`r.minutes` and a couple of lowercase/spaced variants, but never the exact `Level`/`Minutes` keys that the app's own `downloadTemplate()` header row produces. Every import silently fell back to blank level and the 20-minute default. Fixed by adding `r.Level`/`r.Minutes` to the fallback chains.
- **CSV parser broke on any Description containing a comma** — `parseCsv` split each line on every `,` with no awareness of quoted fields, so a quoted Description like `"Southwest, Great Plains, Eastern Woodlands"` shifted every subsequent column (Level, Minutes) out of alignment for that row.
